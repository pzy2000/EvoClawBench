We thank the reviewer for the careful, detailed reading. We address each point below.

**Single run / variance.** We agree and already flag this in Limitations ("Experimental coverage"): one run per task/mode, with repeated seeds and confidence intervals left as future work. As partial mitigation, our judge-robustness check (regrading 36 hybrid-task outputs with an alternate judge) gives Pearson r=0.997 (mean |Δ|=0.014); a second alternate judge gives r=0.951 — so grading noise alone is unlikely to explain the reported swings.

**Same sub-problems in first/second run.** We agree; this is exactly what our Limitations "Transfer scope" paragraph already states: PostSkill reruns the same task/fixtures, measuring within-task distillation, not transfer to unseen sub-problems. We did not intend the results to be read as a transfer claim, and we will sharpen this wording. A train/eval sub-problem split, as suggested, is a natural next revision.

**Catastrophic drops with 0 skills created.** This is the most important point, and the reviewer's own hypothesis — "breakdown in workflow" — is exactly what we found on inspection. For the two most extreme OpenClaw rows (and the nanobot row the reviewer likely has in mind, 77.77%→0.99%), the affected batches show a very high share of empty/failed API responses (roughly 250-270 of ~300 logged calls returning no content/zero tokens) rather than any skill-content or prompt effect, consistent with the upstream API endpoint being unstable during that run. That is also why 0 skills were produced: the first, skill-authoring pass already failed to get usable model output, so PostSkill's second pass inherited the same failure rather than being misled by a bad skill. As a direct check, we re-ran the same nanobot + DeepSeek-V4-Pro configuration on a separate, stable endpoint (12-task hybrid subset used elsewhere in the paper): Baseline 9.7%, PreSkill 18.5%, PostSkill 76.7% (first pass 79.5%, second pass 76.7%) — once the endpoint is stable, PostSkill behaves normally and skill reuse is not catastrophic. We also re-ran OpenClaw/GPT-5.4 end-to-end on the full 101-task suite on the same stable endpoint and observe zero empty/no-reply responses throughout, versus the 250+/300 seen in the affected original batch. We will finish the remaining reruns and report the corrected numbers as an explicit erratum/replacement rather than silently editing Table 2.

**Table 7 empty-skill scaffold (+19.84).** We already flag this ourselves: an empty scaffold outperforming real skill content (19.84 vs 4.05 points) is presented as evidence that part of the measured gain is attributable to the reuse prompt / context reset / run-to-run variance rather than skill content — not as a positive result — and we explicitly caveat it as a 4-task, single-run diagnostic rather than a headline claim.

**Cost/usage analysis.**
- *End-to-end definition*: End-to-end = first execution + skill authoring/summarization + second execution (PostSkill); Execution-only isolates only the final attempt. We will restate this as an explicit sum rather than an incremental description to remove ambiguity.
- *"Only skill creation + second run"*: the harness already records per-task phase-level usage (`first_execution` / `skill_summary` / `second_execution`) that was not previously rolled up in the paper. Aggregating it post hoc: for the three OpenClaw rows with intact PostSkill data, "reuse-only" usage (skill-summary + second execution, excluding the first, baseline-equivalent pass) still uses roughly 2.4-2.7x as many tokens as Baseline — so even under this more favorable accounting the overhead remains substantial rather than disappearing.
- *Runtime for the Finding-3 ratios*: the five reported efficiency ratios (0.38/0.30, 0.21/0.26, 0.32/0.28, 0.36, 0.40) are all OpenClaw rows; we will label them explicitly so this is not ambiguous.
- *Nanobot data gap*: while producing the phase-level breakdown above we found nanobot's usage extraction returns 0 tokens for several model/provider pairs even on fully successful runs. We will note this explicitly as a reporting gap in that adapter rather than leave it implicit.

**Workspace isolation granularity.** To answer directly: isolation is per task-run (and per phase within PreSkill/PostSkill), not per sub-problem — all sub-problems of one task are given to the agent inside a single prompt/session in one workspace. We will state this explicitly in the Task Suite/Workspace text and adjust Figure 1's caption so it is unambiguous.

We believe re-running the affected rows, adding the phase-level cost breakdown, and tightening the wording above will materially strengthen the paper's central claims, and we thank the reviewer for pushing on exactly the points that mattered most.
