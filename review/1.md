Paper Summary:
Paper proposes a benchmark to evaluate if and how skill creation can be helpful to agentic systems which need to solve problems of similar nature multiple times. The main finding is that there is significant sensitivity to harness used, skills don't seem to help (and can significantly hurt) performance, while using more tokens/time/resources. However some of the findings could be problematic as detailed below.

Summary Of Strengths:
I appreciate the care in which the benchmark is set up, e.g. that workspaces are cleared for each task/sub-problem, and the consideration of how systems should be judged in terms of explicit outputs rather than in conversation.

The paper has very good approach to reproducibility of benchmark artefacts, although some details could be improved, e.g. specific versions of backends, harnesses and judges.

Summary Of Weaknesses:
The reported results are from a single run, it would be nice to have more runs to understand how variable/sensitive are these results.

The set up, of the same task (and all sub-problems) being solved by agent, during both first run and second run (in case of postskill), is a bit problematic, especially if this is meant to be used as a benchmark, because it can be gamed to over-fit to the (sub-problems) in the task. I think a better set up is to split the sub-problems into a "train" and a "eval" set. This will also address the question (described later) of unfairness to postskill re usage costs (which is currently solving the same task twice).

The paper reported significant effectiveness drops from baseline to pre/post-skill setups. These happen seemingly randomly, and are very drastic, e.g. going from 78% solve rate to 0%. Given the drastic drops, I think it would be prudent to analyse what caused these reductions in performance to understand what went wrong. It is possible, for example, that the created skills, or the prompting/scaffolding surrounding the use of skills, completely led the systems down wrong paths inadvertently, or that the additional skills overloaded the context memory. More careful structuring/prompting of how skills should be created and used (along with caveats re reliability of these skills) could all mitigate these catastrophic drops significantly. It is also very strange to me that in fact in some of the most catastrophic drops in performance for postskill, the number of skills created was 0. In this situation shouldn't the second run behave essentially the same as baseline? Any differences indicate either breakdown in workflow, or extreme sensitivity to the prompts. This result is further compounded by the (in my opinion) strange result in Table 7 that an empty-skill scaffold increased performance by 19.84. How can this be consistent with postskill getting much worse performance with 0 skills? I think a detailed analysis of these are called for, for the conclusions of the paper to stand up to criticisms.

The analysis and discussion around usage costs is quite weak.

End-to-end usage costs: From what I understand, for postskill, this is first run cost, plus skill creation, plus second run cost, with the first run being (I think) essentially identical to baseline run (no skill). So the overall end-to-end usage costs is significantly unfair to postskill. It might be more informative to report the breakdown in costs across these phases, and also more detailed breakdown in terms of input/output tokens, due to the differences in pricing (and true underlying compute costs) of input vs output tokens.
Also, the actual reported numbers in Tables 5 and 7 are quite limited in scope. It would be nice to see usage numbers for all rows in Table 2 across baseline, preskill, postskill, and split into first run, skill creation and second run.
I think the paper is presupposing that a efficiency gain of < 1 means skill creation/usage is less attractive than baseline. Given that the usage costs for postskill already includes a first (effectively baseline) run, I don't think this is a fair comparison. At least report usage that includes only skill creation and second run.
Also, are the reported efficiency gains on page 7 text for openclaw or nanobot?

It is unclear whether the the workspace is isolated per sub-problem, or per task. The main text seem unclear about this point, though Figure 1 indicates per sub-problem. Please clarify.
